# Dogfood findings, 2026-09-03

Findings from installing Legion 0.3.13 on Windows and using it, plus what
survived validation of two external reviews. `docs/pending/README.md` is
generated by `scripts/check-atomic-canons.mjs` and cannot hold hand-written
entries, so they live here.

## Open packaging & evidence defects (dogfood, 2026-09-03)

Confirmed against installed Legion 0.3.13 and repo `main` @ `be46ba0e` while validating two external
reviews. Not capability atoms; recorded here because each is open, reproducible, and blocks a shipped
surface. Full evidence in [DOGFOOD.md](../DOGFOOD.md) §4 and §6.

| # | Defect | Evidence | A fix must |
|---|---|---|---|
| DF-1 | **Fixed.** The nine declared plugin hook events never reached any client, so Guard was unregistered on Claude Code | `src/registry/plugin-surface.json` declares `counts.hookEvents: 9`, sourced from the repo-root `hooks/hooks.json` by `scripts/verify-plugin-parity.mjs:172`; `assemblePortableCore(...)` at `scripts/assemble-native-release.mjs:440-451` takes no hooks input, so `<plugin root>/hooks/hooks.json` is absent on the installed projection and `claude plugin details legion@skills-dir` reports `Hooks (0)` | **Done**: `hooks/hooks.json` now ships in the portable core (`@rightkit/ax` carries it, the assembler passes it, and the plugin-root validator requires it). Verified on the installed product: `claude plugin details legion@skills-dir` reports Hooks (9). |
| DF-2 | **Fixed.** Packaged validators could not run from an installed plugin root (five wrappers, not two) | Both wrappers set `PACKAGE_ROOT = Path(__file__).resolve().parents[3]` and `runpy` into `src/lib/*-validator/`, which the portable core does not ship; on the installed projection they raise `FileNotFoundError: … legion\src\lib\dispatch-validator\validate-tasklist.py` and `… validate-dispatch.py`. The tasklist wrapper also points at the **dispatch** validator directory | **Done**: five wrappers were affected (`tasklist`, `dispatch`, `handoff` ×2, `coder`), not two. Each engine is now vendored into its skill bundle and each wrapper resolves the bundled copy first, falling back to the repository path for development. Verified by running all four from a simulated installed plugin root, where the previous wrappers raise `FileNotFoundError`. The tasklist wrapper's two targets are **not** a bug: `tasklist-validator/` serves legacy Markdown packets and `dispatch-validator/` the current generation, and both files exist |
| DF-3 | The `audit` skill invokes a runner the projection does not ship (references half **fixed**) | `skills/audit/SKILL.md:49` invokes `node <package-root>/tools/audit/audit-run.mjs`, and no `tools/` directory exists under the plugin root; separately `skills/audit/references/{manual,lens-routing}.md` cite `references/audit-design-decisions.md`, `coverage-and-trajectory.md`, `lens-cues.md`, `migration-safety.md`, `ponytail-lens.md`, all five of which exist only at the repo-root `references/` and are absent from `skills/audit/references/` | **Done**: the five lens references now ship inside `skills/audit/references/` and the manifest is refreshed. **Still open**: `skills/audit/SKILL.md:49` names `node <package-root>/tools/audit/audit-run.mjs` as the primary path, and no `tools/` ships in the plugin root, so an installed product always takes the degraded `legion audit` fallback. Choosing which runner is canonical for the installed product is a design decision, not a mechanical fix. Plain relative links are also invisible to the digest verifier, so add a link check that resolves them inside the bundle |
| DF-4 | **Fixed.** A plugin MCP manifest must be `.mcp.json`; Legion shipped only `mcp.json` | `<plugin root>/mcp.json` exists with the correct `${PLUGIN_ROOT}` token form, yet `claude plugin details legion@skills-dir` reports `MCP servers (0)`. Legion's MCP still works because setup registers `mcpServers.legion` and `[mcp_servers.legion]` at user-config level — a different mechanism | **Done**: the core now carries `.mcp.json` (and `.claude-plugin/plugin.json`, `mcp_config.json`) directly. Verified: `claude plugin details` reports MCP servers (1). |
| DF-5 | **Fixed.** The installed 0.3.13 binary rejected its own portable core over `publicAgents` | `legion serve --stdio --plugin-root <plugin root>` prints `portable plugin root rejected: rightax-portable-core.json is invalid: unknown field publicAgents … at line 34 column 16`. Fixed in `main` by `aa4f6101` (`engine/bins/legion/src/cli.rs:301`), **not** in the installed build | **Done**: verified on the installed build — `legion serve --stdio --plugin-root <installed>` probes exit 0 with no stderr. |
| DF-6 | **Fixed.** `legion_m1_status` over MCP always answered `complete` while the CLI answered `incomplete` | `engine/bins/legion/src/cli.rs:1121` unconditionally inserts `json!("complete")` in `m1_status_value`, which backs the MCP tool at `cli.rs:1082`; `native_m1_status` at `cli.rs:1163-1183` reports `"status": "incomplete"`, `"fidelity": "degraded"` with three named gaps | **Done**: the slice claim is now `sliceStatus`, the MCP tool reports the product's real status, and the gap list has one owner so the two paths cannot drift. |
| DF-7 | **Fixed.** `tests/e2e/qualification.test.mjs` could not run and no CI lane noticed | `tests/e2e/qualification.test.mjs:6` imports `../../scripts/qualify-release.mjs`, which does not exist; `node --test tests/e2e/qualification.test.mjs` fails at import. `pnpm test` globs only `tests/*.test.mjs`, so `tests/e2e/` is never executed | **Done**: the suite it depended on was deleted with its removed subject, and `pnpm test` now globs `tests/**/*.test.mjs`. That widening exposed 17 failures across 58 files CI had never run; all are fixed or recorded (DF-8, DF-9). |
| DF-8 | 13 coverage records claim `measured-pack` coverage against corpora absent from the repository | `src/registry/coverage/index.json` marks `language.javascript`, `language.python`, `language.rust`, `language.go`, `language.jvm`, `language.dotnet`, `language.c-family`, `language.php-ruby`, `language.mobile`, `language.long-tail`, `framework.frontend`, `framework.backend`, `framework.data` as measured, but `bench/corpora/` does not exist, so `validateCoverageRegistry` throws `ENOENT … bench/corpora/javascript`. The registry asserts measured coverage it cannot substantiate | Either ship the corpora or drop those records to an unmeasured tier. Tracked as a `todo` in `tests/coverage/registry-v2.test.mjs` so the claim stays visible rather than silently passing |
| DF-9 | `validateCoverageRegistry` could never read its default provider registry | `src/lib/coverage/index.mjs:6` resolved `ROOT` with `'../..'` from `src/lib/coverage/`, landing on `src/`, so the default path became `src/src/registry/providers.json` and every call without an explicit `root` threw `ENOENT`. **Fixed**: `ROOT` now resolves `'../../..'` | Closed |
| DF-10 | **Fixed.** The installer aborted on any machine with a client open | `Legion-0.3.13-windows-x86_64-setup.exe /VERYSILENT` returned exit 5 and left the previous version in place, because `legion serve --stdio` — the MCP server a client launched — held the installed binary and Windows will not replace a running executable. Only reproducible while the product is actually in use, which is the normal case | **Done**: a `PrepareToInstall` step stops `legion.exe`, `legion-hook.exe` and `legion-mcp.exe` before the copy; clients restart the MCP server on their next request |
| DF-11 | **Fixed.** Upgrades never reached any client | The installer swapped the `current` junction and updated PATH but never refreshed the client projections, so after every upgrade all five clients kept serving the previous version's skills until someone re-ran setup by hand | **Done**: the installer runs `legion setup repair --confirm` after cutover |
| DF-12 | **Fixed.** `setup repair` was permanently red | It refused a Legion entry in `config.toml` carrying no ownership marker — what an older build wrote — with no way to resolve it, so the refresh in DF-11 would have failed on every upgrade forever | **Done**: an entry byte-identical to what this version would write is adopted; anything the operator authored is still refused. The removal range no longer steps back over the line above the table, which on an unmarked entry belongs to the operator |
| DF-13 | **Fixed.** Every client held a private copy of the whole skill tree | Six copies of 817 files: the installed `current/plugin` plus `.claude`, `.codex`, `.cursor`, `.antigravity` and `.agents`. `.codex` and `.cursor` were already byte-identical to the source; only three client descriptor files (`.claude-plugin/plugin.json`, `.mcp.json`, `mcp_config.json`) differed, and each was a copy of a file already in the core. An edit in one client was silently absent from the other four, contradicting Legion being the canonical source for the skills it ships | **Done**: the core carries the three descriptors, and a full plugin root is now a link to the installed tree. An operator-made link (one client pointed at another) is respected and never replaced; inspection accepts a linked root while still refusing any link below it; removal deletes the link rather than walking it, which would otherwise have deleted the installed product |
