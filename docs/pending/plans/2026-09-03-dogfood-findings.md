## Open packaging & evidence defects (dogfood, 2026-09-03)

Confirmed against installed Legion 0.3.13 and repo `main` @ `be46ba0e` while validating two external
reviews. Not capability atoms; recorded here because each is open, reproducible, and blocks a shipped
surface. Full evidence in [DOGFOOD.md](../DOGFOOD.md) §4 and §6.

| # | Defect | Evidence | A fix must |
|---|---|---|---|
| DF-1 | The nine declared plugin hook events never reach any client, so Guard is unregistered on Claude Code — not degraded, absent | `src/registry/plugin-surface.json` declares `counts.hookEvents: 9`, sourced from the repo-root `hooks/hooks.json` by `scripts/verify-plugin-parity.mjs:172`; `assemblePortableCore(...)` at `scripts/assemble-native-release.mjs:440-451` takes no hooks input, so `<plugin root>/hooks/hooks.json` is absent on the installed projection and `claude plugin details legion@skills-dir` reports `Hooks (0)` | Package `hooks/hooks.json` into the portable core, declare it in the core contract the way `publicAgents` now is, and add a parity check that fails assembly when a declared surface count has no packaged artifact |
| DF-2 | The `tasklist` and `dispatch` packaged validators cannot run from an installed plugin root | Both wrappers set `PACKAGE_ROOT = Path(__file__).resolve().parents[3]` and `runpy` into `src/lib/*-validator/`, which the portable core does not ship; on the installed projection they raise `FileNotFoundError: … legion\src\lib\dispatch-validator\validate-tasklist.py` and `… validate-dispatch.py`. The tasklist wrapper also points at the **dispatch** validator directory | Package both validator engines inside their skill bundles (or inline them), fix the tasklist wrapper's wrong target directory, and smoke-run both wrappers from the assembled plugin root, not from the repo |
| DF-3 | The `audit` skill references artifacts the projection does not ship | `skills/audit/SKILL.md:49` invokes `node <package-root>/tools/audit/audit-run.mjs`, and no `tools/` directory exists under the plugin root; separately `skills/audit/references/{manual,lens-routing}.md` cite `references/audit-design-decisions.md`, `coverage-and-trajectory.md`, `lens-cues.md`, `migration-safety.md`, `ponytail-lens.md`, all five of which exist only at the repo-root `references/` and are absent from `skills/audit/references/` | Either package the runner and the five lens references inside the `audit` bundle, or re-point the references to a class the registry allows and drop the `tools/` invocation. Plain relative links are invisible to the digest verifier, so add a link check that resolves them inside the bundle |
| DF-4 | A plugin MCP manifest must be `.mcp.json`; Legion ships `mcp.json` | `<plugin root>/mcp.json` exists with the correct `${PLUGIN_ROOT}` token form, yet `claude plugin details legion@skills-dir` reports `MCP servers (0)`. Legion's MCP still works because setup registers `mcpServers.legion` and `[mcp_servers.legion]` at user-config level — a different mechanism | Emit the plugin-level manifest as `.mcp.json`, keep the user-level registration, and assert the details count is 1 in plugin parity |
| DF-5 | The installed 0.3.13 binary rejects its own portable core over `publicAgents` | `legion serve --stdio --plugin-root <plugin root>` prints `portable plugin root rejected: rightax-portable-core.json is invalid: unknown field publicAgents … at line 34 column 16`. Fixed in `main` by `aa4f6101` (`engine/bins/legion/src/cli.rs:301`), **not** in the installed build | Ship a build containing `aa4f6101` and re-run the probe; latent only because both hosts invoke bare `legion serve --stdio` |
| DF-6 | `legion_m1_status` over MCP always answers `complete` while the CLI answers `incomplete` | `engine/bins/legion/src/cli.rs:1121` unconditionally inserts `json!("complete")` in `m1_status_value`, which backs the MCP tool at `cli.rs:1082`; `native_m1_status` at `cli.rs:1163-1183` reports `"status": "incomplete"`, `"fidelity": "degraded"` with three named gaps | Propagate the honest status into `m1_status_value`, or rename the MCP field so it cannot be read as product status |
| DF-7 | `tests/e2e/qualification.test.mjs` cannot run and no CI lane notices | `tests/e2e/qualification.test.mjs:6` imports `../../scripts/qualify-release.mjs`, which does not exist; `node --test tests/e2e/qualification.test.mjs` fails at import. `pnpm test` globs only `tests/*.test.mjs`, so `tests/e2e/` is never executed | Delete the test or re-point it at `scripts/qualify-windows-release.mjs`, and make the test glob cover `tests/e2e/` so a dead import fails CI |
| DF-8 | 13 coverage records claim `measured-pack` coverage against corpora absent from the repository | `src/registry/coverage/index.json` marks `language.javascript`, `language.python`, `language.rust`, `language.go`, `language.jvm`, `language.dotnet`, `language.c-family`, `language.php-ruby`, `language.mobile`, `language.long-tail`, `framework.frontend`, `framework.backend`, `framework.data` as measured, but `bench/corpora/` does not exist, so `validateCoverageRegistry` throws `ENOENT … bench/corpora/javascript`. The registry asserts measured coverage it cannot substantiate | Either ship the corpora or drop those records to an unmeasured tier. Tracked as a `todo` in `tests/coverage/registry-v2.test.mjs` so the claim stays visible rather than silently passing |
| DF-9 | `validateCoverageRegistry` could never read its default provider registry | `src/lib/coverage/index.mjs:6` resolved `ROOT` with `'../..'` from `src/lib/coverage/`, landing on `src/`, so the default path became `src/src/registry/providers.json` and every call without an explicit `root` threw `ENOENT`. **Fixed**: `ROOT` now resolves `'../../..'` | Closed |
