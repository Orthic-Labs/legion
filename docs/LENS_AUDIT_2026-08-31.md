## The dominant finding: the enforcement layer is currently dark

**None of the three Rust binaries the system depends on are built or on PATH.** `which legion` / `legion-hook` / `legion-mcp` → not found; `engine/target/` does not exist. Yet:
- `hooks/hooks.json` wires every lifecycle event to bare command `legion-hook`.
- `.claude-plugin/plugin.json` declares the MCP server as `legion serve --stdio`.
- `skills/audit/dependencies.json` hard-depends on the `legion` host capability.

`src/registry/capabilities.json` documents that an unresolvable hook command **"fails open and silently: … every Guard gate stops running with no operator-visible signal and no effect-decision receipt is recorded."** So right now the platform's skills, doctrine, and manifests describe a working orchestration system while the actual Guard-enforcement and MCP surfaces are no-ops that fail *quietly*. This is consistent with the reset — but **there is no build/install script anywhere in the tree** (no Makefile, no install.sh) to close the gap, so a fresh clone lands in exactly this silently-degraded state with nothing to guide it out. **Highest-priority action: add a documented `build + link binaries` step, and make the hook fail *loud* (visible block) rather than open when its binary is absent.**

## Security / correctness

1. **MCP tool effects are ungated end-to-end via a verb-allowlist heuristic (design HIGH / live MEDIUM). Confirmed by direct read + a dedicated deep-trace.** `parse_effect_class` classifies an MCP tool as an external effect only via `is_mcp_external_tool` → `is_mcp_external_operation`, matching solely the tokens `write`/`send`/`delete` in the tool name. An MCP tool whose name lacks those verbs and whose payload has no `command` field (e.g. `mcp__fs__create`, `mcp__fs__put`, `mcp__shell__run`, `mcp__github__push_files`, `mcp__http__post`, `mcp__db__exec`) returns `None` → the `Ok(None)` branch → `HookResponse::allowed("MCP tool carries no external effect")` **before any policy object is even constructed** ([main.rs:99-106,1009-1013,1179-1206](engine/bins/legion-hook/src/main.rs:1179)). A follow-up trace confirmed **nothing downstream catches it**: `PostToolUse` unconditionally returns `allowed` ("post-effect observation accepted") with no re-classification; `Stop` only validates an Oracle receipt; lifecycle events are generic-allowed; and no effect-reconciliation path exists in the hook. MCP tool names are third-party-controlled, so this allowlist-of-3-verbs is a denylist an untrusted server can dodge, and the effect is never recorded. Live severity is MEDIUM only because (a) the hook binary isn't currently built (see top finding), and (b) Guard is defense-in-depth atop the host's own MCP permissioning. Fix: classify any unrecognized MCP tool as `EXTERNAL_SIDE_EFFECT` (fail-closed to adjudication) rather than `None`, or require an explicit per-tool effect declaration.

2. **RESOLVED (was an open question): the live path IS fail-closed — via a different evaluator than first assumed.** The deep-trace confirmed `legion-hook` → `authorize_effect` → `NativeApplication::authorize_hook` → `LegionEngine::authorize_effect` → **`CanonicalEffectPolicy::authorize`** over `legion_contracts::policy::PolicyPack` — NOT `legion_policy::PolicyEvaluator::evaluate` (which lives on the separate M1 capability-invocation path) and NOT the `legion-effects::EffectExecutor` (which has no production caller at all). `CanonicalEffectPolicy` is genuinely default-deny: deny on missing/`None` policy, deny on no-matching-rule, deny on `allowed:false`, deny on unresolved approval/trust fields, and `authorize_effect` maps any `Err` to `HookResponse::denied`. Default-allow only for `FILE_WRITE`/`FILE_MOVE`/`VCS_COMMIT`/`COMMAND_EXEC`/ordinary `FILE_DELETE`; `EXTERNAL_SIDE_EFFECT`/`NETWORK_EGRESS`/`PROCESS_SPAWN`/`CREDENTIAL_ACCESS`/`PUBLISH`/`VCS_PUSH`/`DEPENDENCY_INSTALL` all default-deny. So when a classified effect reaches it, enforcement is sound — the only hole is finding 1 (effects that never get classified). Note for cleanup: `legion-effects::EffectExecutor` (provably fail-closed on unseal/non-immutable) is a **parallel unused surface** — either wire it in or treat it as dead alongside `legion-testkit`. [legion-application/src/lib.rs:1629-1671](engine/crates/legion-application/src/lib.rs:1629), [legion-runtime/src/engine.rs:299-304](engine/crates/legion-runtime/src/engine.rs:299)

**Verified clean (scoped to files read):** the M1 `legion-policy` evaluator is also default-deny at every stage; frozen-provider-plan reconciliation never reports incomplete coverage as clean (traced execution→report→verify with a dedicated test); `legion-mcp` is stdio-only with a fail-closed `ReleaseBindingGate`; no secrets in tree (all matches are detector test fixtures); commit/alchemist skill prose explicitly forbids `git add -A`/destructive staging.

## Architecture

3. **Crate graph is clean** — acyclic, correctly layered (`contracts` base → `policy-model` → `policy` → `effects` → `provider-sdk` → `runtime` → `application`); the effect path is structurally forced through policy by the dependency graph. No cycles.
4. **`legion-host` is a naming/scope trap** — largest crate (8,100 LOC) but it's the installer/host-projection module (writes agent/plugin files into a consuming host), not a runtime "host." It sits confusingly beside `legion-runtime`/`legion-policy` and is not reachable from the two enforcement bins (`legion-hook`/`legion-mcp` depend only on application/contracts/runtime). Rename or split for clarity; not a security issue.
5. **Doctrine's three authority roles are asymmetric in the skill layer** — Alchemist and Oracle have full `skills/` packages; **Sage has none** (only `agents/sage.md` + `src/roster/sage.md`), despite AGENTS.md/doctrine framing the three symmetrically. Confirm deliberate vs a package dropped in the reset (the 2026-08-29 internal audit already repaired related Sage/Oracle/Alchemist doctrine drift — this class of drift is recurring here).
