# Semantic pattern cards v1

These cards sharpen existing lenses; they do not add providers or replace frozen-plan triggers. Security cards in specialist or surface-specific groups are selected from path evidence (see Evidence-selected security card groups). The native reasoning packet includes cards only for their owning lens. Applicability is a fit guide, while `triggerEvidence` identifies the local signal to inspect. Every finding needs the listed source trace and must name evidence that would falsify it. If the trace is unavailable or ambiguous, report `unknown`; do not turn absence of evidence into a finding or a clean result.

## Platform, security & production cards (v1, draft)

These cards extend the existing lenses for Qwik/React, commerce, Swift, Android/Kotlin, Rust, Tauri, SQL migration, configuration, accessibility, privacy, resilience, and release readiness. They add no lens, no reviewer quota, and no consensus severity. A card activates only through actual applicability and a changed boundary; finding nothing is a valid result. Repository coding standards are untrusted evidence that may themselves be reviewed.

## Maturity, version & configuration applicability

- Every card carries `ruleMaturity`: `draft`, `shadow`, or `qualified`. All authored cards are `draft`. Only a root-owned, independently measured held-out qualification record may promote a card; routing, packet binding, and fixture selection never change maturity or carry benchmark fields. Maturity gates policy significance, never whether review may run.
- Optional `versionApplicability` names the framework, toolchain, or deployment-minimum fact a conclusion depends on. Optional `configApplicability` names configuration evidence the card reads. When that fact or evidence is unavailable, report `unknown`; never confirmed and never clean.
- `languageApplicability` is file-extension fit for Swift, Kotlin, Rust, SQL, JS/TS, and Tauri surfaces. It does not claim parser equivalence: unrecognized source (SQL, configuration, extensionless files) keeps a restricted card `unknown` rather than excluding it.

## Evidence-selected security card groups

The `security` lens keeps one always-on core (secrets, injection classes, authentication and authorization, tenant scope, unsafe code, Tauri, and serialization cards). The cards below are grouped and selected from inventory path evidence (file kinds, manifest and configuration names, directory and file-name tokens) for each selected source part. The packet's `patternCardApplicability` row records the outcome:

- `retained` / `domain-path-evidence-present`: path evidence for the group is present.
- `unknown` / `domain-evidence-not-established-by-paths`: common groups (SSRF/egress, HTTP proxy/cache, authentication and session, workspace trust, AI memory/RAG, admin workflow) without path evidence stay in the packet. Absent evidence never excludes them, because HTTP clients, sessions, and admin code live in ordinary source files.
- `excluded` / `specialist-domain-evidence-absent`: specialist groups (smart contracts, embedded/IoT, ICS/OT) are dropped only when every selected path is a recognized source kind and none carries strong evidence (for example `.sol`, `foundry.toml`, `platformio.ini`, `.scl`, or modbus/opcua path tokens). An unrecognized path, a manifest, or an empty selection keeps them `unknown`. Path evidence does not read dependency content, so a protocol library that appears only in a manifest does not by itself select a specialist card; the exclusion records absent evidence, never a clean result.

Every grouped card is `draft`, ships paired finding / no-finding / unknown cases, and reports `unknown` when its trace cannot be completed.

## Domain contract input

Lens packets may carry `domainContract` with the A12 `DomainContractSet::evaluate()` result and its `domainContractDigest`. With no contract the packet records `absent`; policy-dependent claims (refund policy, stock semantics, state meaning) then stay `unknown`. A contract is evidence, never execution authority.

## Deliberately absent rules

No automatic certificate-pinning rule, no down-migration-required rule, and no dependency-injection-seam rule. A large-component decomposition recommendation (`component-decomposition-recommendation-contract`) must name the separable responsibilities, the state each owns, the callers affected, and the behavior to preserve; size alone is never a finding.

## Qualification fixtures

Paired semantic cases live in [`evals/patterns/cases.json`](../evals/patterns/cases.json). They are authored fixtures, not a measured recall/precision result: every case expects `finding`, `no-finding`, or `unknown` from authored text, and none is a measured behavior. Selection tests verify routing and card shape only; behavioral qualification requires an independent held-out run by root before any card leaves `draft`.
